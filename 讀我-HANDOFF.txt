★★★★★ 2026-09-26 第三輪（v2.6.2 → v2.6.3 / sw v27 → v28，修正立體渲染鏡頭取景留白）
--------------------------------------------------------------------------------
使用者截圖問一句:「2.5d,線與擋板有到最底嗎」——先老實承認:沒有,而且是我在上一輪
CLAUDE.md 裡自己寫過「這是刻意的取捨,不是 bug」的那個限制,這輪被使用者的截圖推翻。

■① 真因——邏輯座標早就到底了,錯的是鏡頭取景
  上一輪已經把 `paddle.y` 移到只剩 28px 離畫布底邊(跟橫向共用同一個常數),數字上沒有錯。
  問題出在 `render3d.js` 的 `resize()`:鏡頭距離是拿「整個球場對角線的一半」去算「這個半徑
  在目前 FOV 下要多遠才塞得進畫面」,直向手機球場又窄又長,這個距離其實是被「左右不能裁到
  磚牆」那頭撐出來的,縱深方向(板子→磚牆)根本用不到那麼遠。但 `camera.updateProjectionMatrix()`
  给的是上下左右**對稱**的視角,多出來的視角配額因為對稱硬要平分掉,整段留在畫面下方
  (板子那一端開闊、沒有牆擋視線,所以那裡看起來特別空)。拿 Playwright 截圖比對量出來:
  板子投影到螢幕後只落在畫面往下約 73~93%(視角度而定)的位置,不是真的貼底。
  ⚠ 這條坑跟前兩輪(危險線、寶物)看起來像但其實不同類:那兩個是「疊層座標系不一樣」,
  這個是「鏡頭取景的視角配額分配方式」——三個坑都指向同一句更大的教訓:**3D 模式裡任何
  「邏輯座標看起來沒錯」的東西,都還要再問一次「投影到螢幕上真的對嗎」,兩者不是同一件事**。

■② 修法——不對稱視錐(off-axis frustum),鏡頭距離與角度完全不動
  左右維持原本對稱公式(`tanHorizHalf = tan(fov/2) * aspect`,那頭本來就抓得緊,不會裁到
  磚牆,不要碰它,免得引入新的裁切風險);上/下拆開分別計算板子那一端(近景,+Z)與磚牆/
  上牆那一端(遠景,−Z)實際投影需要的角度,直接用 `camera.projectionMatrix.makePerspective
  (left, right, top, bottom, near, far)` 蓋掉原本 `updateProjectionMatrix()` 算出來的對稱矩陣。
  ⚠ 三個要記住的細節:①改完矩陣後 `camera.projectionMatrixInverse` 要手動同步(`.copy(...).invert()`),
  沒同步的話某些用到反矩陣的功能(這支目前沒有用到,但以後如果加滑鼠拾取/射線之類的功能會炸)
  會用到舊的反矩陣 ②往後**不能再呼叫** `camera.updateProjectionMatrix()`,那會用回對稱公式蓋掉
  這個修正 ③板子那端留 12% 餘裕、磚牆那端留 20% 餘裕(磚牆那頭本來就不是玩家在意的區域,
  留寬一點更安全),不是切齊 0 邊界貼死。

■③ 新增驗收(`window.__render3dDebug().paddleScreenFrac`,+1 項,共 26 項)
  把板子的世界座標拿 `THREE.Vector3.project(camera)` 投影成 NDC,換算成「離螢幕最下緣的比例」
  (0=貼底、1=頂到最上緣),斷言 > 0.85。比截圖比對更精準,也比只看世界座標更誠實——世界座標
  對不代表投影到螢幕上就對,這正是這次踩到的坑。★ 已用手動換回舊版 `render3d.js`(舊版
  debug hook 沒有這個欄位)驗證這條測試對舊版真的會抓到:斷言乾淨失敗,不是擺著好看的斷言。
  修好之後直向手機量到 `paddleScreenFrac ≈ 0.883`。

■④ 驗收:node --check ×2、既有三支零相依測試全綠、`verify-browser.mjs`(2D)全綠、
  `verify-browser-3d.mjs` 26 項全綠(本機驗證;上線後另外驗兩個正式網址)。橫向也拍了截圖
  確認沒有引入新的裁切(側牆、磚牆、板子左右都還在畫面內)。

★★★★★ 2026-09-26（v2.6.0 → v2.6.1 / sw v25 → v26，修正立體渲染的危險線對齊）
--------------------------------------------------------------------------------
使用者實機截圖回報:「擋板要在最最下面,為何擋板下方有一條線?」——先查證那是「危險線」
(標準/挑戰難度磚牆定時下移的警戒線)+ 直向拇指區,回報是設計如此、2D/3D 量出來的座標一致。
使用者又貼一張 3D 截圖糾正:「2.5d,線是在擋板下面」+ 要求「線與擋板再往下移一些,但不用到底」。

■① 真因:危險線曾經只是 2D 疊層上的一條線(固定螢幕百分比的平面映射),板子是透視投影
  的 3D 物件——同一個 canvasY 在兩套映射下對不上,板子(近景,透視放大)反而畫到「線」
  (平面,不受透視影響)的上面。拿真實截圖比對(Playwright 截圖 + 量 DOM/mesh 座標)才抓到,
  單看 canvasY 數字(dangerLineY=932 < paddleY=958,邏輯上線在板子上方)完全看不出問題——
  這正是「數字對、畫面錯」的典型案例。
  ⇒ 修法:危險線改成 `render3d.js` 自己的 3D 物件(`dangerLineMesh`),跟板子吃同一顆鏡頭、
  同一套透視,兩者相對位置在任何鏡頭角度下都保證一致,不是再猜一個位移量去湊視覺對齊。
  `game.js` 的 `render3dFrame()` 不再對 3D 模式呼叫 `drawDangerLine()`,改算一份
  `{active, y, color, opacity}` 丟進 `syncScene()` 的 payload。

■② 順手處理使用者的第二個請求:直向手機的「拇指區」(`getPaddleBottomGap()`)從
  畫布高度 8.5% 收到 6.5%,板子(與跟著它算的危險線)往下靠近底邊一些。
  ⚠ 不是砍到很小:`test/patterns.mjs` 有一條「拇指區至少要留畫布高度 6%」的安全網,
  這條線是先前為了不讓單手直握時手指擋住板子本身而定下來的下限,這輪只退讓到略高於
  下限,沒有吃掉這個安全邊界。要退讓更多要先跟使用者確認能接受手指可能碰到板子的風險。

■③ 新增的驗收(`test/verify-browser-3d.mjs`):直接比 3D 場景裡兩個 mesh 的 Z 座標
  (`dangerLinePos[2] < paddlePos[2]`),不比螢幕像素——鏡頭角度以後再怎麼調,只要 Z 座標
  的相對順序對,畫面上的相對順序就保證對,比截圖比對更不會因為調鏡頭參數而假紅。
  ★ 有實際證明這條測試抓得到這個 bug:把 `render3d.js`/`game.js` 退回舊版重跑,
  `dangerLineVisible` 立刻變 false(舊版從沒建過這個 3D 物件),不是擺著好看的斷言。

■④ 驗收:node --check ×2、既有三支零相依測試全綠(含 `test/patterns.mjs` 的拇指區安全網)、
  `verify-browser.mjs`(2D)全綠、`verify-browser-3d.mjs` 22 項全綠(本機/pages.dev/netlify.app
  三邊都跑過)。

■⑤ 沉澱:3D 場景裡任何要跟「3D 物件」比相對位置的東西,哪怕它本身邏輯上是平面/2D 的
  (一條線、一塊 HUD 提示),只要要跟 3D 物件對齊,就得進 3D 場景本身、吃同一套投影,
  不能留在扁平疊層裡用「同一份座標數字」蒙混過去——這條之後加其他「疊層元素」時要記得。


★★★★★ 2026-09-25（v2.5.0 → v2.6.0 / sw v24 → v25，立體渲染 3D 模式）
--------------------------------------------------------------------------------
使用者連問三句：「打磚塊，能做 3D 版嗎？」→「2.5D 與 3D，都是另開一支嗎？」→
「舊網站能 2D 與 2.5D，切換嗎？」，最後拍板：**同一支 repo 加開關**，不另開站。
（0917 那則交接曾記過「3D 打磚塊要開新 repo」的舊構想，這輪使用者當面改了主意——
 以下面這輪的決定為準，那則舊記錄留著純供對照，不代表現況。）

■① 設計決定寫在 CLAUDE.md「立體渲染（3D）模式的設計決定」段，這裡只講重點：
  物理/存檔/分享碼/關卡編輯器/Boss/寶物**一行都沒動**（含 0917 剛做完的板子長度），
  只加一支新的渲染層：
    · `render3d.js`（ES module，只在玩家打開設定裡的「立體渲染（3D）」開關那一刻
      才用動態 `import()` 載入，2D 玩家不用多下載 Three.js）
    · `vendor/three.module.js`（Three.js ES module build，下載進 repo 的靜態檔案，
      沒有走 CDN、沒有 npm）
  畫面上兩塊 canvas 疊在一起：`#gameCanvas3d`（新）在下面畫地板/磚塊/板子/球本體，
  `#gameCanvas`（舊，2D）疊在上面變透明，只留危險線/道具/子彈/護盾條/磚塊耐打度數字/
  浮動分數/狀態列這些「不是實體方塊」的疊層——這些次要系統完全沒有 3D 化，省下大量成本。

■② 兩個真的會咬人的坑（都寫進 CLAUDE.md 對應章節，這裡只記結論）
  ⚠ WebGL 預設 `preserveDrawingBuffer:false`：畫面本身完全正常，但任何事後用
    `drawImage`/`toDataURL` 讀 3D 那塊 canvas 的驗收腳本會讀到一片空白，
    誤判成「3D 什麼都沒畫出來」——這輪真的中過一次，花了一段時間才查到根因。
    已在 `render3d.js` 的 WebGLRenderer 設定裡開 `preserveDrawingBuffer:true`。
  ⚠ `test/verify-browser-3d.mjs` 所有情境都開 context 選項 `serviceWorkers:"block"`——
    這支只在意 3D 渲染本身，裝著 SW 會引來兩顆跟 3D 完全無關的坑，都是真的中過才知道：
    ① 測 render3d.js 載入失敗的退回邏輯時，`page.route()` 攔 `render3d.js` 的請求在
      **已裝上 Service Worker 的分頁裡攔不到**（SW 自己的 fetch 事件處理常式會把
      已預先快取的檔案直接端出來，不經過那個路徑）。
    ② 對著**剛部署完、這台瀏覽器沒造訪過**的 netlify.app 首次實測：`sw.js` 的
      `clients.claim()` 觸發的 `window.location.reload()` 會在頁面「看起來已經穩定」
      之後幾百毫秒才發生，剛好攔腰打斷「勾選開關→按開始→點畫布」這段互動，畫面被換回
      最初的設定頁——症狀完全不像「reload 打斷了」，反而很像轉橫向後版面跑掉、
      或設定沒生效，連續好幾支獨立診斷腳本才追出真因。固定多睡幾秒能降低撞見的機率
      但躲不掉（reload 的時間點跟網路狀況一起飄），乾脆整支測試都不裝 SW。
    已寫進 `test/verify-browser-3d.mjs` 與 `CLAUDE.md` 對應段，下次維護這條測試不要重踩。

■③ 鏡頭角度是刻意的取捨,不是沒調好:固定俯角（47°）+ 依球場對角線動態算距離,
  寧可多留白也絕不裁到磚塊或板子。代價是直向手機（球場瘦長）鏡頭被迫拉遠、偏向俯視，
  橫向（球場較扁）立體感明顯很多。之後想加強直向,思路是「依長寬比動態調俯角」,這輪沒做。

■④ 驗收:node --check game.js/render3d.js、既有三支零相依測試(patterns/sharecode/
  sharecard)全綠(3D 完全沒碰到這幾支測的東西)、`test/verify-browser.mjs`(2D 回歸)
  60 項全綠、新的 `test/verify-browser-3d.mjs` 19 項全綠(含切換/resize/偏好持久化/
  載入失敗退回 2D、轉橫向後仍在遊戲畫面)。三邊(本機/pages.dev/netlify.app)都跑過。

■⑤ 部署:CLAUDE.md 的部署段 dist 複製清單已經補上 `render3d.js` 與整個 `vendor/`
  資料夾——Netlify 那份因為 publish 是整個根目錄不會漏,但 **CF Pages 手動部署那份
  漏複製這兩樣的話,打開 3D 開關會 404**,已修好那段腳本。

■⑥ 這一輪合併時撞見另一台機同時在改本 repo（0917 那份板子長度五段），
  APP_VERSION／CACHE_NAME 兩邊都想用同一個號碼——已改成疊加：

■① 為什麼「直向」不是改 CSS 就好（這是整輪的重點）

  打磚塊本來就是直式街機（Breakout / Arkanoid 的原生機台是直立螢幕），
  直向反而更接近原型。但這個遊戲有三件事讓它不能直接塞進去：

    ① 畫布是被 CSS 拉滿整個視窗的（width/height:100%）⇒ **邏輯長寬比一旦和真實
       視窗差太多，整個畫面就被非等比拉扯壓扁**。舊版邏輯畫布永遠是 560 高、
       長寬比夾在 1.45~2.55 ⇒ 直向（真實比例 0.5）會被壓成一團
       —— 這才是當初必須擋住直向、掛「請轉為橫向」的真正原因。
    ② 直向的落球距離大約是橫向的 2.7 倍 ⇒ 同樣的 px/frame 會變成「等球」。
    ③ 板寬是絕對 px（136）⇒ 在 560 寬的畫布上佔掉四分之一個螢幕，難度整個垮掉。

  解法：**同一份程式、兩組版面常數**，規則是「短邊永遠 560」，長邊由視窗比例推。
  常數都在 `PORTRAIT_*`。要跟著縮的是「跟場地比例有關」的量（板寬、球/寶物/子彈/
  落石速度、下壓間隔），**不用縮**的是絕對 px 的大小（球半徑、寶物）——
  因為兩個方向的 邏輯px→CSSpx 比例本來就接近，在真手機上看起來一樣大。

  直向實際值（iPhone 390×844）：畫布 560×1063、磚 46×39、列距 47、
  板寬 69（橫向是 136）、球速 ×1.5、板子下方留 9% 高的拇指區。

■② 最容易壞、又最不會被發現的一段：玩到一半轉手機

  座標全是絕對 px。換版面沒搬 ⇒ 球留在畫面外、磚塊橫著溢出、板子卡在右邊界，
  而語法檢查與單元測試全綠。所以 `resizeCanvasForScreen()` 換完尺寸一定要

    · 下壓的位移靠新的 `state.descendRows` 帶過去 —— 不帶的話，轉一次手機

    · 球/板/寶物/落石按比例搬，速度乘上兩個版面的 speedScale 比

■① 先找到真正的病根：每一次部署都推給了沒人看的那一份

    （bash exit 127 / PowerShell 真正的退出碼是 -1073740791 = 0xC0000409
      STATUS_STACK_BUFFER_OVERRUN，原生層硬崩所以 Node 印不出任何東西；
      開 WRANGLER_LOG=debug 只會看到 CF API 全回 200 然後就沒了）。

    ★ 真正的觸發條件是 **cwd 路徑含非 ASCII 字元**，不是「在 git repo 裡」。
      而且 `pages deploy` 與 Workers 的 `wrangler deploy` **兩種模式都中**，
      連 `--dry-run`（根本不上傳）也崩；`--assets` 指向純 ASCII 目錄救不了，
      因為決定的是 cwd 不是路徑參數。唯讀指令（--version / project list）不受影響。
      這個 repo 的路徑是 Desktop\codex打磚塊，正好踩中。
      當天實測三組：
        ASCII 路徑 + git repo（emoji 多行 commit） → 乾淨成功
        中文路徑  + git repo                       → 上傳前就死，連 Uploading... 都沒有

    ★★ 為什麼「有時做完才死、有時還沒做就死」：0xC0000409 是**記憶體毀損**被偵測到，
      崩潰點本來就不固定。這個 repo 穩定在做完前就死（輸出導到檔案確認不是緩衝被吃掉，
      deployment list 也確認沒有新部署），但別的中文目錄會做完才死。

      .wrangler/cache/wrangler-account.json 寫進去並當成靜態資產公開（另一顆雷）。

     所有命。改成扣一命並把磚塊往回推三格。
