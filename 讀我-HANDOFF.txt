■② 怎麼做的:一個倍率,不是第二套板寬

  PADDLE_SIZES(xs .7 / s .85 / m 1 / l 1.25 / xl 1.6)乘在難度給的板寬上,
  存在 preferences.paddleSize(與難度分開存:改難度不會把長度洗掉)。
  板寬的唯一算式仍然只有一條:getPaddleBaseWidth() = 難度板寬 × 倍率 × getPaddleScale()。
  直向實測(畫布 560 寬 / iPhone 390):標準 69px(≈48 CSS px)、超長 111(≈77)、極短 48(≈33)。

■③ 這輪真正的地雷:板寬最後會走 clamp,而下限本來寫死 100

  標準難度選「極短」是 136×0.7=95.2 ⇒ **會被悄悄夾回 100**,選單有反應、板子沒變短,
  而 node --check、既有單元測試、甚至截圖都是綠的(差 5px 肉眼看不出來)。
  ⇒ getPaddleMinWidth() 改成 Math.min(100, 難度板寬×倍率)、
    getPaddleMaxWidth() 改成 Math.max(260, 難度板寬×倍率 + PADDLE_EXPAND_STEP)。
  上限那個 +EXPAND_STEP 是**測試抓出來的**:休閒×超長 = 164×1.6 = 262 > 260 ⇒
  max === base ⇒ 加寬寶物與卡關輔助雙雙變成「吃了沒反應」的道具。

■④ 誠實的數字(沿用 0916 圖卡那條鐵則)

  板長不是預設時,遊戲標題、排行榜列、每日挑戰圖卡都會標出來 ——
  同一張榜上「超長板 3000 分」和「極短板 3000 分」不是同一件事。
  ★ 板長是跟著**那一筆成績**存的(topScores[].paddle / records.dailyToday.paddle),
    舊紀錄沒有這個欄位就不標,**不可以拿做卡當下的設定去標昨天打的分數**。

■⑤ 順手修掉的既有隱患

  雙板寶物的影子板寬寫死 clamp(…, 72, 150) ⇒ 直向標準板寬才 69,影子板反而比本體還寬
  (選極短更只有 48)。改成跟著 getPaddleScale() 一起縮。

■① 為什麼「直向」不是改 CSS 就好（這是整輪的重點）

  打磚塊本來就是直式街機（Breakout / Arkanoid 的原生機台是直立螢幕），
  直向反而更接近原型。但這個遊戲有三件事讓它不能直接塞進去：

    ① 畫布是被 CSS 拉滿整個視窗的（width/height:100%）⇒ **邏輯長寬比一旦和真實
       視窗差太多，整個畫面就被非等比拉扯壓扁**。舊版邏輯畫布永遠是 560 高、
       長寬比夾在 1.45~2.55 ⇒ 直向（真實比例 0.5）會被壓成一團
       —— 這才是當初必須擋住直向、掛「請轉為橫向」的真正原因。
    ② 直向的落球距離大約是橫向的 2.7 倍 ⇒ 同樣的 px/frame 會變成「等球」。
    ③ 板寬是絕對 px（136）⇒ 在 560 寬的畫布上佔掉四分之一個螢幕，難度整個垮掉。

  解法：**同一份程式、兩組版面常數**，規則是「短邊永遠 560」，長邊由視窗比例推。
  常數都在 `PORTRAIT_*`。要跟著縮的是「跟場地比例有關」的量（板寬、球/寶物/子彈/
  落石速度、下壓間隔），**不用縮**的是絕對 px 的大小（球半徑、寶物）——
  因為兩個方向的 邏輯px→CSSpx 比例本來就接近，在真手機上看起來一樣大。

  直向實際值（iPhone 390×844）：畫布 560×1063、磚 46×39、列距 47、
  板寬 69（橫向是 136）、球速 ×1.5、板子下方留 9% 高的拇指區。

■② 最容易壞、又最不會被發現的一段：玩到一半轉手機

  座標全是絕對 px。換版面沒搬 ⇒ 球留在畫面外、磚塊橫著溢出、板子卡在右邊界，
  而語法檢查與單元測試全綠。所以 `resizeCanvasForScreen()` 換完尺寸一定要
  `rescaleWorld()`：
    · 磚塊走 `relayoutBricks()` 照 **row/col 重排**，不是等比例縮
      （磚塊是格狀的，縮過去會和新版面的邊距對不齊，幾關之後整面走鐘）
    · 下壓的位移靠新的 `state.descendRows` 帶過去 —— 不帶的話，轉一次手機
      就等於送玩家一個免費重置
    · 球/板/寶物/落石按比例搬，速度乘上兩個版面的 speedScale 比

  已進 `test/verify-browser.mjs` 當常駐迴歸（轉過去、轉回來各驗一次）。

■③ 順手修掉一個**本來就存在**的隱患：續玩存檔沒有記「存的時候多寬」

  存檔存的是絕對座標，而橫向畫布的寬度本來就會隨裝置在 812~1428 之間變動
  ⇒ 在寬螢幕存、窄螢幕續玩，磚塊本來就會溢出。以前沒人回報是因為大家都用同一支手機。
  現在存檔帶 `cw/ch/pt/pb`（`RUN_SAVE_VERSION` 3→4，舊存檔自動作廢），
  還原時放進 `pendingRestoreLayout`，由下一次 resize 換算。
  ⚠ 因此 `restoreRun()` 裡的板寬**故意不夾上下限** —— 那時的數字還是舊版面的單位。

■④ 使用者可以選回舊行為

  設定頁多一個「畫面方向」：自動（預設）/ 固定橫向。選固定橫向＝完全的舊行為，
  含「請轉為橫向」蓋版與 `screen.orientation.lock`。
  manifest 的 `orientation` 從 `landscape` 改成 `any` —— 鎖著的話，
  裝成 App 的人連轉都轉不了（runtime 那把鎖在「固定橫向」時照常生效）。

    https://bricksbreaking.pages.dev     手動 wrangler 部署   作品集卡片連的是這份

     以後 deploy-drift-scan 抓得到它。

  ⚠ wrangler 的地雷（花了四次失敗才找到，判準後來還被別場的反例修正過一次）：
    在這個 repo 目錄裡跑 `wrangler pages deploy` 會印完橫幅就無聲崩潰
    （bash exit 127 / PowerShell 真正的退出碼是 -1073740791 = 0xC0000409
      STATUS_STACK_BUFFER_OVERRUN，原生層硬崩所以 Node 印不出任何東西；
      開 WRANGLER_LOG=debug 只會看到 CF API 全回 200 然後就沒了）。

    ★ 真正的觸發條件是 **cwd 路徑含非 ASCII 字元**，不是「在 git repo 裡」。
      而且 `pages deploy` 與 Workers 的 `wrangler deploy` **兩種模式都中**，
      連 `--dry-run`（根本不上傳）也崩；`--assets` 指向純 ASCII 目錄救不了，
      因為決定的是 cwd 不是路徑參數。唯讀指令（--version / project list）不受影響。
      這個 repo 的路徑是 Desktop\codex打磚塊，正好踩中。
      當天實測三組：
        ASCII 路徑 + git repo（emoji 多行 commit） → 乾淨成功
        中文路徑  + git repo                       → 上傳前就死，連 Uploading... 都沒有
        中文路徑  + 非 git                          → 上傳成功但行程仍以崩潰碼退出
      （這個判準被改過兩次，兩次都是別場的反例逼出來的：初版寫「在 repo 目錄裡」，
        被 dragtetris 在 repo 目錄裡部署成功打掉；二版寫「中文路徑+git 才會上傳前死」，
        被我自己做的「帶 remote、長 emoji 多行 commit 的中文 git repo 卻做得完」打掉。）

    ★★ 為什麼「有時做完才死、有時還沒做就死」：0xC0000409 是**記憶體毀損**被偵測到，
      崩潰點本來就不固定。這個 repo 穩定在做完前就死（輸出導到檔案確認不是緩衝被吃掉，
      deployment list 也確認沒有新部署），但別的中文目錄會做完才死。
      ⇒ 不要預測會是哪一種，非 ASCII cwd 一律當成不能用。

    ⇒ 修法：Push-Location 到一個**純 ASCII 的「空」目錄**（$env:TEMP 即可）。
      「空目錄」不是多寫的：cwd 若就是 assets 夾，wrangler 會把含 Cloudflare 帳號 id 的
      .wrangler/cache/wrangler-account.json 寫進去並當成靜態資產公開（另一顆雷）。
      部署目錄給絕對路徑。完整指令在 CLAUDE.md。
    ⚠ 「中文路徑 + 非 git」那組最陰：部署其實成功了但退出碼是崩潰碼 ⇒
      用 $LASTEXITCODE 或 && 串接的腳本會判成失敗。CF Pages 的結果要看
      `wrangler pages deployment list` 或線上指紋，不要只看退出碼。

■② 統計：三層 beacon 補齊了

  原本只鋪了「開啟」與「停留」兩層，沒有 `-done` 完賽打點。
  已補上艦隊慣例的 window.psDone()，在 loseLife() 生命歸零處呼叫。

  另外查證了一件事：**-dwell 的程式碼沒有壞**。線上實測 `-dwell&t=6` 正常送出，
  同款程式碼的 dianzhu-tai 停留 1:42 也正常入帳。那 25 次開啟真的沒有任何一次
  停留滿 3 秒（8/15~8/20 集中爆發後完全歸零，是爬蟲/預覽流量的形狀）。
  ⇒ 這也正是補 -done 的價值：-dwell 靠 pagehide，無頭爬蟲被 kill 時根本不會送，

■④ 三個「差點做錯、值得記住」的設計判斷

  ㈠ 震屏一度用 random() —— 那是每日挑戰的 seeded RNG。畫面每多震一幀就偷走
     一個亂數，同一天同一關的磚塊配置會跟著「震了幾幀」而變。
     ⇒ 純視覺的隨機一律用 Math.random()。已寫測試把這條釘死。
  ㈡ 卡關輔助的觸發原本規劃「連死 3 次」，但標準難度只有 3 條命 ——
     第 3 次失誤就是 Game Over，設 3 等於永遠來不及出手。改成 2 次。
  ㈢ 磚塊下壓撞線若直接 Game Over，復活後磚塊還壓在線上 ⇒ 復活即死、一次吃光
     所有命。改成扣一命並把磚塊往回推三格。
     ⇒ 通則：會扣命的環境傷害一定要附「推回去」的補償。

■⑨ 接手時怎麼驗「現在到底是哪一版」

  本機：   grep CACHE_NAME sw.js ； grep 'APP_VERSION =' game.js
  線上：   curl -s "https://bricksbreaking.netlify.app/sw.js?b=1"   | grep CACHE_NAME
           curl -s "https://bricksbreaking.pages.dev/sw.js?b=1"     | grep CACHE_NAME
  ⚠ /index.html 在 CF Pages 是 308 轉到 /，curl 要加 -L，否則 body 是空的，
    grep 出來會像「檔案沒上去」（這一輪誤判過一次）。
  三邊都應該是 breakout-pwa-v21 / 2.3.0。

  git：    git status --short                 （應為空）
           git rev-list --count @{u}..HEAD    （應為 0 = 真的推上去了）
           git log --oneline -1
  ⚠ 這裡刻意不寫死某一顆 SHA —— 交接 commit 本身就會推進 HEAD，
    寫死的那一顆隔一個 commit 就是錯的（這份文件第一版就犯過）。
    要對版就看「最後一顆功能 commit」：519b077 = v2.3.0 每日挑戰分享圖卡，
    它之後只應該有文件類的 commit。
